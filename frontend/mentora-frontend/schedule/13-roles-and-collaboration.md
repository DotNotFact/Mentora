# 13 — Роли, гостевой просмотр и групповое обучение по ссылке

Статус: [ ] не начата

## Контекст

Администратор (2026-08-05) явно попросил: гость может смотреть, но
ничего не может делать; пользователь может покупать курсы, а также
приглашать других/быть приглашённым в группу для прохождения курса;
курсы создают "кураторы/инструктора/учителя, админы" — то есть ролей
предполагается больше, чем нынешние три.

Найдено при подготовке задачи: `UserRole` — сгенерированный тип
(`src/shared/api/generated/models/userRole.ts`, из `openapi/openapi.yaml`)
со значениями ровно `student | instructor | admin`. Значения "guest" там
нет и не должно быть в этом виде — гость в этой архитектуре означает
"нет сессии/токена вообще" (см. `AuthGuard`, `features/auth/store.ts`),
а не отдельную строку в enum роли аутентифицированного пользователя.
Никакого понятия "группа"/"когорта"/"инвайт-ссылка" в кодовой базе
сейчас не существует (проверено — нет ни одного `features/groups`,
ни `invite`, ни `cohort`).

## Цель

1. Формализовать гостевой (неаутентифицированный) просмотр как явный,
   проверенный режим — не новую роль.
2. Решить вопрос "кураторы/инструктора/учителя" — не плодить роли без
   разделения прав, если для этого нет причины (см. "Продуктовое
   решение" ниже).
3. Добавить групповое прохождение курса по инвайт-ссылке — студент
   может пригласить других в свою "группу" для одного курса, или
   инструктор/куратор/админ может создать группу и разослать ссылку
   для вступления.

## Продуктовое решение (принято при подготовке, не переспрашивать)

- **НЕ добавлять отдельные роли `curator`/`teacher`.** Формулировка
  администратора ("кураторы/инструктора/учителя") читается как
  синонимичный ряд для одной и той же функции — "тот, кто создаёт
  курсы", а не как описание трёх разных уровней прав. Добавление трёх
  новых enum-значений в `UserRole` без разницы в правах — это
  сложность без пользы (три бэкенд-роли, которые everywhere ведут себя
  идентично). Вместо этого: `instructor` остаётся единственной
  "создающей" ролью в `UserRole`, а UI-копирайт может называть её
  "куратор курса"/"преподаватель" контекстно (например, `CourseCard`
  показывает "Автор курса", не "Instructor"). Если администратору
  позже понадобится реальное разделение прав (например, куратор может
  редактировать чужие курсы, а обычный инструктор — только свои) — это
  отдельная будущая задача с собственным обоснованием, не эта.
- **Guest = отсутствие сессии, не новое значение `UserRole`.** Задача —
  аудит, а не новая модель данных: пройтись по каталогу/детали
  курса/публичному профилю инструктора и убедиться, что
  неаутентифицированный пользователь видит контент, но кнопки
  "Записаться"/"Купить"/"Оставить отзыв" либо скрыты за явным
  CTA "Войдите, чтобы записаться", либо ведут на `/login` с сохранением
  intended-маршрута (проверить, есть ли уже такой redirect-паттерн у
  `AuthGuard` — если нет, добавить).

## Шаги

1. **Гостевой аудит.** Пройтись по `/`, `/courses`, `/courses/$id`
   (публичная часть) без токена — зафиксировать, какие элементы должны
   быть видны, какие скрыты/задизейблены. Обновить
   `docs/architecture/frontend-structure.md` или
   `.agents/skills/mentora-design/SKILL.md`, если там нет явного
   раздела про гостевой режим.
2. **Группы — модель данных (фронтенд-контракт).** Добавить в
   `openapi/openapi.yaml` черновой контракт: `Group` (id, courseId,
   ownerId, inviteCode/inviteUrl, memberIds, createdAt, expiresAt?
   maxMembers?), эндпоинты create/join-by-code/leave/list-members.
   Перегенерировать (`yarn api:generate`) — это ЕДИНСТВЕННОЕ место в
   проекте, где меняется openapi-контракт вручную (мок, реального
   бэкенда нет — см. `openapi/README.md` про плейсхолдер-спеку).
3. **Feature-модуль `features/groups/`.** По конвенции проекта:
   `components/`, `hooks/` (TanStack Query), `store.ts` (только
   UI-state — например состояние модалки создания группы), `schemas.ts`
   (Zod для формы создания группы).
4. **UI создания группы.** На странице курса (для уже записавшегося
   студента) или в форме записи — кнопка "Пригласить группу"/
   "Учиться вместе" → генерирует ссылку вида `/invite/$code`.
   Инструктор/админ видит то же на странице управления своим курсом,
   плюс список активных групп с числом участников.
5. **UI вступления по ссылке.** Роут `/invite/$code`:
   - гость → предложение зарегистрироваться/войти, после чего —
     автоматическое вступление в группу и (если применимо) запись на
     курс;
   - уже аутентифицированный пользователь без записи на курс →
     подтверждение "Вступить в группу «...» и записаться на курс
     «...»?";
   - истёкшая/неверная ссылка → понятная ошибка, не голый 404.
6. Обновить `AuthGuard`/роутинг, чтобы intended-маршрут (включая
   `/invite/$code`) сохранялся через редирект на `/login` и
   пользователь возвращается на него после входа.
7. Скриншот-гейт для новых экранов (создание группы, страница
   вступления, гостевой каталог) — 375/768/1280px.

## Дизайн-заметки

Групповое приглашение — не chat/real-time фича, простая
ссылка-код + список участников. Не проектировать под будущие вещи вроде
ролей "модератор группы" — вне объёма.

## Критерии готовности

- Гость не может выполнить ни одного мутирующего действия (запись,
  покупка, отзыв) — все такие точки входа либо скрыты, либо ведут на
  `/login` с возвратом на исходный intended-маршрут.
- `UserRole` не расширен без явного нового обоснования (остаётся
  `student | instructor | admin`).
- Ссылка-приглашение работает end-to-end: создание → раздача →
  вступление (гостем и аутентифицированным пользователем) → отображение
  в списке участников группы.
- `yarn verify` зелёный, e2e-тест на happy path приглашения
  (`tests/e2e/`).

## Не входит

Разделение прав внутри "создающей" роли (куратор vs инструктор с разным
доступом), модерация групп, чаты/уведомления внутри группы, платные
групповые тарифы (скидки за группу) — отдельные будущие задачи при
явном запросе.
